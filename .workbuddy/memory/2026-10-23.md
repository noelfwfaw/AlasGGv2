## 第四轮：更新数据 + 干员培养（两个 MAA 新任务类型）

- MAA GUI 的「更新数据」`UserDataUpdate` 不是核心任务，而是 GUI 组合：追加 `OperBox` + `Depot`
  两个核心任务（都无参数），识别结果由 GUI 保存/导出（可从一图流 OpenAPI 取 box，再上传/导出）。
  「干员培养」对应核心任务 `OperProgress`。
- 回调：都走 `SubTaskExtraInfo`(20003)，靠 `what` 区分：
  - `OperBoxInfo`：`details.done` + `all_opers` + `own_opers`(id/name/elite/level/potential/rarity)；
  - `DepotInfo`：`details.done` + `details.data`，**data 是字符串化的 JSON**（`{"itemId": count}`），要二次 loads；
  - `OperProgressDetail`：role/name/result/result_detail；`done=true` 才是识别结束，false 是中间进度。
- `OperProgress` 参数只有 `plans`（数组），每项 `{role?, name, elite?1~2, skill_level?2~7, skill_mastery?[3]{0~3}}`，
  三个养成动作只写其一；MaaCore 会校验干员名与职业（不存在/缺 plans 时 append 返回 0），
  `role` 可选，同名不同职业必须给（枚举 Warrior/Pioneer/Medic/Tank/Sniper/Caster/Support/Special）。
- 桥接层新增两个任务组：
  - `MaaDataUpdate`（UpdateOperBox/UpdateDepot，均默认 true）→ `maa_start('OperBox'/'Depot')`，
    结果写 `config/maa/operbox.json`、`config/maa/depot.json`（放子目录，避免被 `os.listdir('./config')`
    的配置扫描当成实例配置文件）。
  - `MaaOperProgress`（Plans textarea，默认 `[]`）→ `maa_start('OperProgress', {'plans': ...})`；
    解析函数 `parse_oper_progress_plans()` 提前校验范围并给出中文错误，格式与 MAA「从剪贴板导入计划」一致。
- 注意 `maa_start` 结束时 `callback_list.clear()`，多任务连续跑时每次启动前都要重新挂回调。




## 第五轮：完成所有任务后的收尾（主页面待机 / 关闭游戏）

- 需求：在 MAA 设置页加「完成所有任务后」的选项——主页面待机 / 关闭游戏。
- 配置项复用桥接层已有的 `Maa.Optimization.WhenTaskQueueEmpty`（原来 `display: hide`，
  且被 `config_update` 每次强制重置成默认值）。改为 `option: [stay_there, close_game]` 并显隐可见；
  四语言补 `完成所有任务后 / 完成所有任務後 / When All Tasks Are Completed / すべてのタスク完了後`
  与选项文案 `主页面待机 / 关闭游戏`。默认仍是 `stay_there`（与 MAA GUI「无动作」一致）。
- 行为实现（`submodule/AlasMaaBridge/maa.py`）：
  - 重写 `get_next_task()`：ALAS 主模块的 close_game 分支依赖 `device.app_stop()` 与 `Restart` 任务，
    MAA 插件两者都没有，所以在等待分支里直接调 MAA 的 `CloseDown`（v6.20.1 里 `CloseDownTask` 存在，
    资源 tasks.json 没有同名链，但 MaaCore 内部实现，`AsstAppendTask` 可用）。
  - 关掉游戏后立刻 `task_call('MaaStartup')` 排在等待之前，等待结束由 `MaaStartup`（StartUp +
    `start_game_enabled=True`）把游戏拉起来；这样即使等待期间配置被改动（`wait_until` 返回 False）也不会带着关掉的游戏去跑任务。
  - `asst` 拆成 `asst`(cached_property) + `load_asst(check_task=True)`，新增 `maa_asst()`：
    等待期间不在任务里，`asst` 的「先插开始唤醒」检查会 `task_stop()` 抛 `TaskEnd` 打断调度循环，故必须绕过。
- 顺手修：`config.py` 的 `SCHEDULER_PRIORITY` 缺 `MaaDataUpdate` / `MaaOperProgress`，
  `Filter.apply` 只保留列出的任务名，这两个任务因此永远排不进队列——已补在 Roguelike 之前。
- 验证：`Asst` 不启动，仅用桩对象跑 `get_next_task` 三个分支（close_game / stay_there / 到点直接跑），
  以及 `ConfigUpdater.config_update` 确认用户选择 `close_game` 不会被重置。

## 第六轮：MuMu 模拟器运行中掉线无法自愈（仅分析，未改代码）

- 现象：13:45 Reward 正常；14:07 Restart 任务首个截图时 `nemu_connect` 返回 0，重试 4 次（约 7s）后
  RequestHumanTakeover，实例退出。
- 结论：不是配置/路径/instance_id 问题——config 分支与搜索实例分支算出的 nemu_folder 与 instance_id=1
  完全一致，且 13:45 同一套参数可用。真实原因是模拟器进程已不存在，而"运行中"的任务路径没有 emulator_start 兜底。
- `emulator_start()` 全仓仅 3 处调用：`module/device/device.py:83`（Device.__init__ 捕获 EmulatorNotRunningError）、
  `alas.py:627`（GG check_fail>3）、`module/gg_handler/gg_handler.py:154/161`。
- `Alas.device` 是 cached_property，`alas.py:606` 只做 `_ = self.device`；Connection.__init__/adb_connect
  只在实例首次构造时跑一次，所以只有"Alas 实例未运行"时才会触发启动模拟器（与用户观察一致）。
- nemu_ipc 截图完全绕过 adb，连 EmulatorNotRunningError 都不会抛（`connection.py:799-810` 是唯一出口）。
- `platform_windows.py:316 emulator_start` 是先 stop 再 start，不能对运行中的模拟器盲调。
- 方案（待实施）：任务边界加 `emulator_check()`（adb `echo pong` 约 20ms，失败则 emulator_start），
  或在 `NemuIpc.nemu_ipc` 里把 connect=0 判定为可恢复并拉起模拟器；重启后需清
  `emulator_instance` / `nemu_ipc` / adb 缓存（MuMu 端口可能 16384→16385）。

### 补充验证（14:38 未开模拟器直接启动实例的日志）

- 正例链条已确认：`Connection.__init__`(connection.py:121) → `adb_connect` 10061
  → 暴力重连 4 端口 + detect_device + `check_mumu_bridge_network`(834) → `connection.py:810` 抛
  `EmulatorNotRunningError` → `Device.__init__`(device.py:77-83) → `emulator_start()` 成功（~13.5s）。
- 判定"是否发生过设备初始化"最快的方式：看日志里有没有 `DEVICE` / `DETECT DEVICE`。14:07 失败那次完全没有。
- 修正 1：`EmulatorNotRunningError` 在运行期也会抛（`adb_reconnect`→`adb_connect`，connection.py:905/909），
  但那时会被 `method/adb.py:67-71` 的 `except Exception` 吞掉，5 次后转成 RequestHumanTakeover，仍无人拉起模拟器。
- 修正 2：`adb_connect` 在 10061 路径上要 ~4.2s（26.676→30.884），做存活探测不能用它，
  应用 `list_device()`（~30ms）或 `iter_running_emulator()`（~17ms）。
- 修正 3：`nemu_connect=0` 也可能只是"模拟器正在启动/卡在 boot"，不能直接等价于"没开"。
