## 第八轮：为 MAA 插件写「关闭模拟器 + 任务前拉起模拟器」提示词

- 产出 `doc/prompt-maa-emulator-recovery.md`（自包含，可直接投喂外部编码代理）。
- 核实到的关键事实（与 ALAS 主模块不同，不能照抄）：
  - MAA 插件 `maa.py:41-47` 的 device 是 `FakeDevice`（所有方法返回 None）；
    而 `alas.py:631` 新增了 `if not self.device.emulator_check(): raise RequestHumanTakeover`，
    → **MAA 插件现在每次任务启动必崩**，这是必须先修的回归（提示词里的 R0）。
  - MAA 配置是 `maa.json`，只有 `MaaEmulator_Serial`，没有 `Emulator_Serial` / `EmulatorInfo_*`，
    所以不能 new `Device()` / `Platform()`（Connection 构造期就要 adb_connect）。
  - `PlatformWindows._emulator_start/_emulator_stop` 只依赖 `execute` / `kill_process_by_regex` 两个
    classmethod，可复用；`emulator_start_watch()` 只认 ALAS 包名，不能复用。
  - MAA 只在 `handler.startup()` 里 `asst.connect()`，其它任务不重连 → 模拟器重启后必须显式 reconnect，
    且必须确保 `MaaStartup`（带 `start_game_enabled`）排进队列，否则「模拟器在、游戏不在」。
  - 关模拟器顺序：先 CloseDown 再关机（否则 MuMu 可能弹「应用无响应」卡住 shutdown）。

## 第十一轮：close_emulator 实测出现 30s 超时告警

- 日志：16:00:49 `Close emulator during wait` → `MuMuManager api -v 0 shutdown_player` → 16:01:19
  `Emulator still in adb device list after 30s, continue anyway`（正好 30.04s）。
- 原因分析：`device.py:emulator_stop_and_wait` 只判断「serial 是否还在 `list_device()`」，**不看状态**；
  而 `list_device()`（connection.py:1011-1035）会原样返回 `host:devices` 的所有行，含 `offline` 残留条目。
  MuMu 关掉后 adb 常驻 `offline`，于是每次都会白等 30s 后走「continue anyway」。
- 次生风险：函数返回 True 但状态未知；19 分钟后 `Restart` 前的 `emulator_check` 依赖 `device_alive()`
  的 `status == 'device'`，若 adb 仍报 device（stale 或仍在关机）会跳过拉起 → Restart 打在死设备上。
- 建议改法：判据改为「serial 不存在 或 status != device」；超时后补 `adb disconnect` + 复核；
  仍不确定则记明确结论日志，而不是只 warning。

## 第十一轮补充：用户确认模拟器确实关闭，修正上一轮的过度推断

- 事实确认：16:00:49 shutdown_player 后模拟器真的关了，30s 超时纯属判据问题。
- 判据：device.py:321 `if not self.list_device().select(serial=self.serial)` 只看「条目存在」不看 status；
  MuMu 关闭后 adb 留下 `offline` 条目，且停止链**从不** adb_disconnect（全仓仅 connection.py:752/878/908），
  所以条目会一直留着 → 每次 close_emulator 必然白等满 30 秒。
- **撤回上一轮的误判**：`device_alive()`（device.py:238-253）判的是 `status == 'device'`，offline 为 False，
  且会补一次 adb_client.connect 复核 → 后续 Restart 的 emulator_check 能正确拉起，不存在「打在死设备上」。
  那 30s 的实际代价只是时间浪费 + 误导性 warning，功能不致命。

## 第十二轮：close_emulator 实测 30s 超时 + 期间 task_call 被吞（未改代码）

- **用户 16:01:07 手动启动 Commission（GUI 写 A.json，NextRun=2020-01-01），任务被吞了**：

  → 不会 reload、不会立即执行，只能等旧 `task.next_run` 16:19:41（迟到 18.5 分钟）。

- **修正上一轮的误判**：16:09 查 `adb devices -l`，16384 已完全不在列表里（也没有 offline 残留），
  说明条目最终消失了 → 不是"永久 offline 残留"，更可能是 8 实例负载下 MuMu 关机本身 >30s，当时 VM 仍活着。
- 真问题（与用户提问的"任务间隔小"直接相关）：`close_emulator` **没有等待时长下限**，

- 建议方向（待用户决定）：① 加等待时长门槛（如 <180s 退回 stay_there）；② `start_watching()` 基准提前到阻塞前；

## 第十六轮：MAA 实例 alas2「关游戏→立刻开游戏」自激死循环，写出修复提示词

- 根因（三条叠加）：`maa.py:661-663` 等待分支 `if needs_startup: task_call('MaaStartup')`，

- close_emulator 分支 `needs_startup = True` 同病且更贵（每轮还要启停模拟器）。
- 修法：删掉等待分支的 `needs_startup` / `task_call` 与配套的二次 continue；
  唤醒只留两处（任务边界 game_alive 判据 + MaaStartup 自身 04:00 调度）。
- 护栏设计：不能用「距上次关闭<180s」判（用户关游戏后 1 分钟内加任务是正常操作会误杀），
  改为「连续 ≥3 次进入等待分支且期间没有执行任何非 MaaStartup 任务」→ critical + Takeover。
- 提示词里否掉了「改成 task_delay 到任务前 N 分钟」这个看似温和的方案：MaaStartup 完成后
  队列仍空，仍会再次被提前 → 同样死循环。

## 第十七轮：MAA 实例启动不拉起模拟器 + 关闭路径打在离线设备上，写出修复提示词
